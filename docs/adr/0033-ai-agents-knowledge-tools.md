# 0033 — AI agents, provider layer, knowledge retrieval & tool security

- **Status:** accepted
- **Date:** 2026-10-09

## Context

Phase 5 lets a client build an AI agent (persona, tone, language, limits), connect it to its own APIs ("did this customer pay?"), give it company documents to answer from, and test it in a text playground that is charged from the prepaid wallet. Phase 7 reuses the same agent for live voice calls, so the configuration, the prompt and the tool rules must be shared, not rebuilt.

The AutoChatix code we studied (read-only) showed what not to repeat:

- function **headers stored in plain text** — any API key a client entered was readable by anyone with database or export access;
- function URLs called **without any SSRF check** — `http://169.254.169.254/` (cloud metadata) or internal services were reachable from our servers;
- function parameters stored as an **unvalidated JSON-schema string** — the model's arguments went to the client's API unchecked;
- knowledge kept in an **OpenAI-hosted vector store** — documents leave our control and the feature is locked to one vendor;
- usage charged **without a per-turn idempotency key** — a retried request could charge twice.

## Options considered

1. **Own provider interface (OpenAI REST + deterministic fake), agent config in MongoDB, our own knowledge store with in-process cosine search, a guarded HTTP executor for functions, per-turn idempotent billing through the Phase 4 engine** — chosen.
2. **OpenAI Assistants / Responses API with hosted file search and tools** — least code, but documents and threads live at OpenAI, no control over tool calls or SSRF, hard to test offline, voice (Realtime) is a different API anyway.
3. **A vector database (pgvector / Qdrant / MongoDB Atlas vector search)** — scales further, but adds infrastructure for a size we do not have yet (≤ 10 bases × 2,000 chunks per account).
4. **An agent framework (LangChain / LlamaIndex)** — large dependency tree, hides the request shape we must control (secrets, logging, billing).

## Decision

Option 1.

| Area           | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider       | `AiProvider { chat, embed }` with an OpenAI REST client (`fetch`, no SDK; retries 2 for 429 / 5xx / network / timeout, `Retry-After` ≤ 10 s; errors → `PROVIDER_UNAVAILABLE` 503 / `PROVIDER_ERROR` 502) and a **fake provider** — deterministic rules (payment claim → payment tool, promise → `save_promise_to_pay` with the date from "Today's date", transfer, goodbye, knowledge question → first sentence of the top chunk, abusive → tone rule, else a persona follow-up; Hinglish unless the user wrote English only) and hashed bag-of-words embeddings (1,536 dims). Dev / tests / E2E use the fake; production must use OpenAI (env rule).                                                                                                                                                                                                                                                    |
| Agent & prompt | Agent document (persona, lines, allowed variables, voice, language mode, tone rules, call behaviour, model, caps, guardrails, fallbacks, knowledge, functions, built-in tools). `compileAgent` is **pure** (no DB, no clock) and snapshot-tested; order: safety rules → recovery rules (RBI fair practice) → language → tone → persona → never-say → customer data (allowed variables only, labelled as data) → conversation lines. Phase 7 calls it with `channel: 'voice'`.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Knowledge      | Files (PDF / DOCX / TXT / MD, magic-byte checked, stored privately) and single web pages → normalised text → chunker (headings → paragraphs → sentences incl. `।` → hard cut, ~3,200 chars, 15 % overlap) → embeddings in batches of 64 → chunks in MongoDB with the source version. Search = in-process cosine over unit vectors + 0.05 keyword boost, LRU cache by bytes (200 MB), invalidated by the knowledge base `version`. Retrieved chunks are framed as reference data inside `<<<KNOWLEDGE … >>>` and the model is told never to follow instructions inside them. `VectorIndex` is an interface so a vector database can replace it.                                                                                                                                                                                                                                                           |
| Tools          | Custom functions are a **parameter list** compiled to both the model's JSON schema and a strict zod validator (bad arguments never reach the API). Secret headers are sealed with AES-256-GCM (key derived from `ENCRYPTION_KEY`) and write-only. The executor resolves DNS first, checks **every** address against block lists (private / loopback / CGNAT always in production; link-local / metadata / multicast always), connects to the checked address (no rebinding), allows ports 80 / 443 / 8000–8999, follows ≤ 2 redirects re-checking each and dropping headers off-origin, caps 64 KB and 1–10 s. `{{contact.*}}` values (full phone, external id) are filled server-side and never shown to the model. Built-ins (end, transfer, disposition, callback, promise, SMS) run **simulated** in Phase 5 and build the conversation outcome. Details: [security.md](../conventions/security.md). |
| Turn runtime   | `runAgentTurn`: gates (agent off, wallet empty, caps stop / fallback) → knowledge → model with tools (≤ 3 rounds, ≤ 10 calls) → reply check (never-say, secret requests, unknown long numbers, threats in recovery mode) with one retry → fallback. One `ai_charge` per turn through `chargeUsage` with key `aiturn:<sessionId>:<clientTurnId>` (text tokens + query embedding tokens); knowledge ingest charges `kbingest:<sourceId>:<version>`. Prepaid only, AI budget applies.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Logging        | Never prompts, persona, messages, knowledge text, header values, full phones or variable values — ids, models, token counts, durations, status / error codes only. Tool-call rows keep redacted arguments and a 500-char redacted preview for 90 days.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Retrieval sizing (bench, `npm run bench:retrieval`, dev laptop):** 3 knowledge bases × 2,000 chunks = 6,000 chunks (the per-agent maximum) → cold search (load + cache) 586 ms, warm p50 9.2 ms · p95 10.1 ms · p99 11.5 ms, vector cache 40 MB. Well inside a voice turn budget; a vector database is not needed at this size.

## Consequences

- No vendor lock-in for knowledge; documents and vectors stay in our database and storage. Changing the embedding model marks bases `stale` until re-indexed.
- Everything is testable offline (fake provider, stub servers, fake resolver / dial) — no network in tests.
- In-process search means every API / worker process holds its own cache (≤ 200 MB); fine at the current limits, revisit with a vector database if limits grow.
- Built-in tools only simulate until Phase 7; live mode throws until then.
- ADR 0021 (voice AI provider) stays **proposed** until the live OpenAI run (`docs/setup/openai.md`) and the Phase 7 Realtime work confirm it.
