# Data map

Every collection and file store, and what happens to its personal data. `src/modules/privacy/erase-map.ts` (contact erasure) and the account export and purge work from this table. `tests/security/data-map.test.ts` fails when a Mongoose model has no row here.

**Erase contact:** `delete` = rows removed · `scrub` = row kept, listed personal fields cleared · `keep` = kept on purpose (reason given) · `none` = no contact data.
**Export:** `yes` = in the account export · `no` = not included (reason in Notes).

## Outside our systems

Chats on the customer's phone, data held by Meta, data sent earlier to a webhook receiver and Google Sheets are not ours to delete. The privacy policy says so.

## Phase 19 continuation storage

`whatsappCampaigns` now includes recurrence/root identifiers, header location and durable
`headerMedia.storageKey` (account-owned business content). `whatsappCampaignRecipients`
adds `sentCounted` for retry-safe counters. `campaigns` adds transport/channel and a
flow-or-agent program; agent campaigns have no fabricated flow ID. Recipient erasure
still deletes campaign recipient links. Account purge now deletes campaign and template
header media as well as message/upload copies. No Meta tokens or SIP secrets are public.
`messageClassificationKnown` records whether Meta explicitly reported number mode; legacy
unknowns are conservatively paced. No new PII-bearing event or catalogue entry was added.

Campaign variable eligibility and sending use the central send-purpose sensitive-field reader. Encrypted values are not copied into audience snapshots or estimates. Call quotes expose account selling prices for an owned sender/contact, with no provider cost/margin fields. Durable media is released only when no campaign references its account-owned key.

## Recorded-voice campaigns (VAPI, Cell24x7)

- `campaigns.voiceApi`: audio / IVR choice, retries, batches (`requestId`, count, state, held
  amount, error code). No personal data.
- `campaignContacts.voiceApi`: batch number, Cell24x7 `requestId`, `receiver10` (the 10-digit
  number sent — **personal data**), provider status, duration, key pressed, IVR disposition.
  Contact erasure overwrites `receiver10` and `dtmf`; later results for that number are ignored.
- `calls` with `provider: 'voice_api'`: one row per final result (no media, transcript or
  recording); scrubbed like other calls.
- Incoming phone calls (Phase 20): `calls.from` is the caller's number (`anonymous` when hidden),
  `calls.inbound` holds the account's own number and route, `calls.missed` the callback state —
  scrubbed with the call like `to` / `from`. Unknown callers become contacts with source
  `inbound_call` (erased like any contact). Logs show numbers masked only.
- `accounts.voiceApi` (enabled, assigned IVR ids, IVR estimate seconds) and
  `flowAudio.providerFiles.cell24x7.audioFileId` (provider audio id, hidden from the API).
- **Sent outside:** the 10-digit numbers (CSV per batch) and the chosen audio file go to
  Cell24x7 (processor). Their copies are not ours to delete; the privacy policy lists them.
  Logs never carry the token or a full number.

## Public API resources (DOCS)

`/api/v1/resources/*` returns minimal views to API keys with `resources:read`: flow / agent names and ids (never graphs, prompts or function secrets), WhatsApp number label / display number / status / quality / tier / calling readiness (never tokens or WABA ids), list and segment names with counts, caller numbers, assigned IVR names and the wallet balance. No contact personal data. WhatsApp bulk campaign recipients and exports give keys masked phones only.

- `accounts.voiceApi.credentials.tokenSealed`: an account's own Cell24x7 API token, sealed with the
  secret box (in the sealed-field registry); API views show only the last 4 characters. The
  account webhook secret is stored as a SHA-256 hash.
- `accounts.sipTrunk.passwordSealed`: an account's own SIP trunk password, sealed (sealed-field
  registry); API views show only whether it is set. It is sent only to our Asterisk over ARI.
