# WhatsApp calls over SIP — research note (T18.21)

Source: Meta, "WhatsApp Cloud API — Calling — SIP" (developers.facebook.com/docs/whatsapp/cloud-api/calling/sip), read 3 Nov 2026. Re-check it before building anything: Meta changes calling rules often.

## What Meta offers

Instead of the Graph API calling endpoints and webhooks (what Phase 12 uses), a number can send its calls to **our SIP server**:

- Signaling over **SIP with TLS** (port 5061 by default). Our certificate must match our SIP domain; Meta drops INVITEs silently on a mismatch.
- **Digest auth**: the user name is the business number, the password is generated by Meta (`GET /<PHONE_NUMBER_ID>/settings?include_sip_credentials=true`).
- Media is WebRTC-style: **Opus**, ICE, **DTLS-SRTP** (or SDES, which skips ICE / DTLS). We must send the first SRTP packet.
- Set up with `POST /<PHONE_NUMBER_ID>/settings` → `calling.sip.status: ENABLED` + one server (`hostname`, `port`). One SIP server per number.
- User-initiated calls arrive as an INVITE from Meta; business-initiated calls are an INVITE from us (407 challenge, then credentials) and still need the user's call permission.
- A number on SIP uses **only** SIP: the Graph calling endpoints stop working for it. Webhooks are off by default (`webhook_delivery` sends only `call_created` / `terminate`).
- Firewall: Meta's IP ranges for signaling **and** media, matched on the packet source.

## What it would mean for us

|                                    | Today (Phase 12, Graph API + our WebRTC)  | Over SIP (Asterisk)                                                                                                            |
| ---------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Media path                         | `werift` WebRTC in Node, Opus in Node     | Asterisk terminates DTLS-SRTP / Opus, ExternalMedia RTP to the same `SipCallLeg` as phone calls                                |
| Code                               | WhatsApp leg, signaling, Opus codec       | Second PJSIP endpoint (`meta`), Opus module (`codec_opus` — not in our image), TLS cert, a `whatsapp` mode in the SIP provider |
| Agent (human) calls in the browser | Works (browser WebRTC to Meta, our relay) | Needs a WebRTC gateway in Asterisk (`res_pjsip` WebSocket) — more work                                                         |
| Ops                                | Nothing extra                             | Public TLS on 5061, Meta IP allowlist, certificate renewals for the SIP name                                                   |
| Permission / limits rules          | Ours (dial guard)                         | Same rules, still ours                                                                                                         |

## Recommendation

**Not now.** The Graph API path works end to end (Phase 12) including browser agent calls, and moving a number to SIP turns that path off for it. Revisit in a later phase only if one of these becomes true: Meta's Graph calling is limited or priced worse, our Node WebRTC media shows quality problems at scale (Phase 20 bulk WhatsApp calling), or the client wants WhatsApp and phone calls on one media server. Effort then: about 1–1.5 weeks (Opus in the Asterisk image, TLS endpoint, provider mode, lab with a SIP TLS client, migration of a test number).
